# GitHub のリポジトリを URL ひとつで動かす「dwev」を作った(BETA)

友だちと一緒にアプリを作っていると、「ちょっと動かして見てほしい」という場面がよくあります。手元で `npm run dev` や `python manage.py runserver` を動かして、スクリーンショットを送って、「ここ、ボタンが押せないんだけど」「あ、それ手元だと動くんだよね」というやりとりを、何度もしました。

だったら、**ブランチを指定するだけで、動いている状態の URL が発行される**仕組みがあればいい。そう思って、自前のプレビューサーバー **dwev** を作りました。

> **BETA / ベストエフォート**です。動作や稼働の保証はなく、予告なく止まったり、データが消えたりします。大事なデータや、本番の運用には使わないでください。

**▶ dwev: https://devbox.clusters-prj.com**(GitHub でログインして、承認されると使えます)

この記事では、何ができるのか、どう作ったのか、そして「他人が書いたコードを動かすサービス」なので特に気をつけたことと、作りながらハマったところを、順に書きます。

## 困っていたこと

作る前に、何が困っていたのかを、はっきりさせました。dwev の「できること」は、その困りごとを、ひっくり返したものです。

**1. ブランチごとの確認が、面倒だった**
別のブランチの動きを確かめるには、`git checkout` をして、依存パッケージを入れ直して、`migrate` して、起動して……と、手順が多くありました。しかも、確認している間は、自分の作業が止まります。「プルリクエストを見てほしい」と言われても、気軽に動かせません。同じことを、レビューする側も、毎回やっています。

→ **ブランチ名を変えるだけで、確認できるようにしたい。**

**2. PC がないと、何もできなかった**
動作の確認は、PC が前提でした。外出先や、移動中に、「ちょっと見てほしい」と言われても、PC を開けないと、動かすこともできません。確認が、いつも「家に帰ってから」になっていました。

→ **スマホだけで、起動から確認まで、終わらせたい。**

**3. スマホでの動作確認が、大変だった**
文化祭のアプリのように、**スマホで見られること**が前提のものを作っていると、スマホでの確認が欠かせません。でも、手元の `localhost` は、スマホからは見られません。同じ Wi-Fi につないで、PC の IP アドレスを調べて、ファイアウォールを開けて……と、毎回、手間がかかります。しかも、PWA や Service Worker、`Secure` 付きの Cookie のように、**https でないと動かない機能**は、それでも確かめられません。

→ **https の URL を発行して、実機のスマホで、そのまま開けるようにしたい。**

**4. 「見てほしい」が、URL ひとつで済まなかった**
友だちに見せるたびに、スクリーンショットや、画面の録画を送っていました。触ってもらうことが、できません。「手元だと動くんだよね」で、話が止まることもありました。

→ **URL を送れば、相手が、自分の端末で触れるようにしたい。**

この4つを、まとめて解決する仕組みとして、dwev を作りました。

## できること

画面は、次の流れだけです。

1. GitHub でログインする(初めての人は、管理者の承認を待ちます)
2. リポジトリの URL、ブランチ、ポート番号を入れて「作成して起動」を押す
3. ビルドが終わると、`https://〜-dev.example.com` のようなプレビュー URL が開ける

細かい機能は、こうです。

- **Dockerfile が無くても動く**: リポジトリの中身から、Node / Django / FastAPI / Flask を自動で判定して、Dockerfile を作ります(下に詳しく書きます)
- **プライベートリポジトリも読める**: GitHub App で許可したリポジトリだけ、読み取り専用で clone します
- **スマホから操作できる**: 外出先で、ブランチを切り替えて起動することも多いので、スマホで困らないようにしました
- **停止してもデータが残る**: 止めて、また起動しても、SQLite などに書いたデータは消えません
- **環境変数を、画面から設定できる**: 値は暗号化して保存し、画面には表示しません

## 構成

```
ブラウザ ─ Cloudflare Tunnel ─ Traefik ─ 各プロジェクトのコンテナ
                               └─ dwev 本体 (Node / Express + SQLite)
                                     └─ socket-proxy ─ Docker API
```

- **公開は Cloudflare Tunnel** で行います。サーバーのポートを、インターネットに開ける必要がありません
- プロジェクトごとに、サブドメイン(`{id}-dev.…`)を発行します。**Traefik** が、Host ヘッダーを見て、対応するコンテナへ振り分けます。コンテナを起動するときに、ラベルでルーティングを設定するだけなので、Traefik 側の設定は、変えなくて済みます
- Docker の操作は、本体から直接ソケットを触らず、**socket-proxy** を挟んで、必要な API だけを許可しています。本体が乗っ取られたときの被害を、小さくするためです
- 本体は Node / Express で、状態(ユーザー、プロジェクト、使用量)は、`node:sqlite` に持たせています。依存パッケージを増やしたくなかったので、標準のものを選びました
- Docker とのやりとりは、`dockerode` で行います。ビルド、起動、停止、状態の確認、ログの取得、CPU の統計まで、すべて API で行います

## Dockerfile が無くても動く

最初は、リポジトリに Dockerfile がある前提で作りました。でも、小さなアプリや、授業・文化祭向けのものでは、Dockerfile が無いことのほうが多いです。そこで、中身から種類を判定して、Dockerfile を作るようにしました。

| 見つかったもの | 判定 | 起動コマンド |
|---|---|---|
| `package.json`(`dev` か `start`) | Node | `npm run dev` など。`yarn.lock` や `pnpm-lock.yaml` があれば、そのパッケージマネージャを使う |
| `manage.py` | Django | `migrate` してから `runserver` |
| `requirements.txt` に `fastapi` | FastAPI | `uvicorn <モジュール>:app` |
| `requirements.txt` に `flask` | Flask | `flask --app <モジュール> run` |

細かい工夫もあります。

- **Vite や Next は、`HOST` や `PORT` の環境変数を見ません**。起動コマンドを見て、`--host 0.0.0.0 --port $PORT` を、引数で渡します
- **フロント用の `package.json` と、Django が同居している**リポジトリもあります。`manage.py` があれば、Python を優先します
- **Dockerfile がある場合は、そちらを必ず使います**。自動判定は、あくまで「無いとき」の代わりです

## 一番気をつけたのは「他人のコードを動かす」こと

このサービスは、承認した人が書いたコードを、そのまま動かします。つまり、**サーバーの中で、他人のコードを実行するサービス**です。悪意がなくても、無限ループや、メモリの食いすぎは起きます。なので、リソースと権限は、かなり絞りました。

### 実行時の制限

| 項目 | 上限 |
|---|---|
| メモリ | 256MB |
| CPU | 0.5 コア |
| プロセス数 | 128 |
| 稼働時間 | 最大 1 時間 |
| ディスクに書けるデータ | 1GB |

最初は、もっと緩い値でした。ただ、実際に動かしてみて、「普通のアプリは、この半分でも動く」と分かったので、**半分に下げました**。足りないアプリだけを、あとから緩めるほうが安全です。

CPU は、「使った時間」を数えています。Docker の stats API で、コンテナが使った CPU の累積時間(ナノ秒)を取り、前回との差を足して、ミリ秒で表示しています。「いま何%」ではなく、「合計でどれだけ使ったか」のほうが、重いコードを見つけやすいです。

### ビルドの制限

`docker build` は、実は危険です。`RUN` や、依存パッケージのインストールスクリプトは、**ビルドの最中に、任意のコマンドを実行できる**からです。

そこで、次のようにしました。

- メモリ・CPU・時間に、上限をかける(時間を超えたら、ビルドを打ち切る)
- ビルド用のコンテナを、実行時と同じ**専用のネットワーク**に置いて、サーバー本体の管理用のアドレスには届かないようにする
- 同時にビルドできる数を、絞る(キューに入れて、順番に処理する)

ネットワークの指定が、ひとつ落とし穴でした。`docker build` の CLI(buildkit)は、ビルドごとに、ネットワークを指定できません。そこで、**CLI を使わず、Docker の API(`/build`)を直接呼ぶ**ことにしました。API なら、ネットワークも、メモリも、CPU も、ビルドごとに指定できます。

ビルドを実際に隔離できているかは、サーバー上で、ビルド用のコンテナから、サーバー本体へつなげないことを、確かめています。

### GitHub のトークン

プライベートリポジトリを読むために、**GitHub App** を作りました(OAuth App ではなく、GitHub App にした理由は、権限を細かく絞れるからです)。

- 権限は、**Contents の読み取りだけ**です
- ログインしたときに、「ユーザートークン」を受け取ります。このトークンで読める範囲は、**「アプリに許可されたリポジトリ」と「ログインした本人の権限」の重なり**だけです。つまり、組織の外の人が使っても、その組織のリポジトリは読めません
- トークンは、AES-GCM で暗号化して、DB に保存します。**clone のときに、dwev 本体のプロセスが使うだけ**で、コンテナにも、ログにも出しません。エラーメッセージの中にトークンが混ざったときは、伏せ字にします
- トークンの有効期限は 8 時間です。切れたら、リフレッシュトークン(最長 6 か月)で更新します。同じ人の更新が同時に走ると、リフレッシュトークンが入れ替わって、片方が失敗するので、**人ごとに更新を 1 つにまとめる**ようにしました
- clone のときのトークンの渡し方は、URL に埋め込まず、`GIT_CONFIG_*` の環境変数で、`github.com` 宛ての `Authorization` ヘッダーとして渡します。URL に入れると、ログや `.git/config` に残ってしまうからです

まず、認証なしで clone を試して、失敗したときだけ、ログインしたユーザーのトークンで、もう一度試します。公開リポジトリには、トークンを使わないようにするためです。

## Aternos 方式の「まだ使っていますか?」

放っておくと、サーバーのリソースは、使われないまま埋まっていきます。「いま誰が使っているか」を、自動で判定するのは難しいので、Minecraft のサーバーサービスの **Aternos** のやり方を、まねしました。**一定時間ごとに、「まだ使っていますか?」と聞いて、押されなければ止める**方式です。

最初は、「アクセスがなければ止める」ことを考えました。でも、「開発中は、ブラウザを開いたまま、アクセスしていない」という場面が、普通にあります。逆に、Bot が定期的にアクセスしてくることもあります。**人間が押すボタン**のほうが、確実でした。

作りながら、いくつか工夫しました。

- **全画面で、赤く脈打つ警告にした**: 最初は、小さなダイアログでした。見逃されて、止まってしまったので、画面全体を覆って、音とタイトルの点滅と、通知も出すようにしました
- **タイマーを、常に表示する**: 「次の確認まで」「最大稼働まで」の残り時間を、いつでも見えるようにしました
- **Bot に押させない**: ボタンを押すときに、**Cloudflare Turnstile** で人間かどうかを確認します。トークンは、ホスト名・アクション名・プロジェクト ID に結び付けて、使い回しできないようにしました。連打にも、レート制限をかけています
- **広告枠を用意した**: 「まだ使っていますか?」の全画面の警告の中に、広告を出せる場所を、空けてあります。**広告、募集中です!** 確認のたびに、必ず目に入る場所です

止める理由は、いくつかあります。**最大稼働時間を超えた**、**確認に応答がなかった**、**(設定しているときは)アクセスがなかった**、**アカウントが止められた**、などです。これらを、まとめて判定する関数に集めて、同じ流れで止めるようにしました。

## ハマったところ

### 停止の判定が、最大 60 秒遅れた

タイマーが 0:00 になっても、止まりませんでした。原因は、見回りの処理が、1 分に 1 回しか動いていなかったことです。CPU の計測や、ディスクの確認のような**重い処理**と、**停止の判定**を、同じ周期で動かしていました。

判定だけを **5 秒ごと**に分けて、重いサンプリングは、60 秒ごとのままにしました。画面側も、期限が近いときだけ、短い間隔で状態を取り直すようにして、0:00 とほぼ同時に、警告や停止が出るようになりました。

### 停止のたびに、データが消えた

最初は、停止するとコンテナを**削除**していました。コンテナの中の SQLite は、そのたびに消えます。「毎回データが消える」と、さすがに使えません。

そこで、**コンテナを消さずに、停止だけする**方式に変えました。起動は、既存のコンテナを `start` するだけです。ただし、設定を変えたり、再ビルドしたりしたときは、コンテナを作り直す必要があります。そのとき、データが消えることを、画面で確認してから進めるようにしました。ストレージの肥大化を防ぐために、長く止まっているコンテナは、日数で掃除します。

### iOS の `prompt()` は、改行を入力できない

環境変数を編集する画面を、最初は `prompt()` で作りました。ところが、スマホで、**複数行を入力できません**。環境変数は、1 行に 1 つなので、これでは使えません。

専用の編集ダイアログを作りました。ブランチ、ポート、環境変数(複数行)を、まとめて編集できます。**既存の環境変数を残して追加・上書きする**モードと、**全て消す**モードも用意しました。値が見えない設計なので、「全部を打ち直す」しかないのは、つらいからです。

### `mysqlclient` がビルドできない

`python:3.12-slim` には、コンパイラも、`pkg-config` も入っていません。`requirements.txt` に `mysqlclient` があると、`pip install` が失敗しました。

自動生成する Dockerfile で、**`mysqlclient` や `psycopg2`(`-binary` ではないもの)が依存に入っているときだけ**、必要なライブラリを apt で入れるようにしました。関係ないアプリでは、イメージを大きくしないためです。

### 落ちたコンテナが「実行中」のまま

アプリが落ちても、画面は「実行中」のままでした。DB の状態を、起動した時点のまま、信じていたからです。

見回りのときに、Docker 側の実際の状態を確かめて、**終了していたら、失敗にして、理由(終了コード、メモリ不足かどうか)を残す**ようにしました。「落ちた」ことと、「なぜ落ちたか」が、画面で分かるだけで、原因探しがずっと楽になります。

## Django を動かしたときの罠

実際に、友だちと作っている Django のアプリを動かして、よくある罠に、いくつか当たりました。同じことをやる人の参考に、残します。

- **`no such table`**: Dockerfile の起動で、`migrate` が走っていませんでした。`ENTRYPOINT` で `migrate` してから、元の `CMD` を `exec` する形にして、解決しました

  ```dockerfile
  ENTRYPOINT ["sh", "-c", "python manage.py migrate --noinput && exec \"$@\"", "sh"]
  ```

  `CMD` を書き換えず、`ENTRYPOINT` を足すだけなので、元の起動オプションは、そのまま使えます
- **管理者がいない**: `createsuperuser --noinput` と、環境変数 `DJANGO_SUPERUSER_*` で、自動で作りました。カスタムユーザーモデルだと、`USERNAME` ではなく、**そのモデルのログイン項目名**(例: `USER_ID`)の環境変数が必要です
- **ワーカーが `SIGKILL` される**: gunicorn のワーカーが、メモリ上限(256MB)を超えて、OOM で殺されていました。ワーカーの数を減らして、解決しました。**「CSS が、最初だけ付かない」という症状**も、ワーカーが落ちている間に、リクエストが失敗していたことが原因のようでした
- **`403 CSRF`**: プロキシの後ろでは、Django は自分を http だと思っています。`CSRF_TRUSTED_ORIGINS` に、**`https://` 付きの URL** を入れる必要があります。アプリが、自分の URL を組み立てる設定(今回は `REQUEST_BASE_URL`)も、同じです
- **Service Worker のキャッシュ**: PWA にしていると、古いページや、古い CSRF トークンが、ブラウザに残ります。環境を変えたら、**サイトデータを消す**のが確実です

## 運用の工夫

- **`.env` の整理**: 設定が増えてきたので、`.env.example` を元に、`.env` を整形し直す `npm run env:sync` を作りました。値は、そのまま残します。設定を足すたびに、「コピーして、戻して」をするのが、面倒だったからです
- **管理画面**: 承認制なので、ユーザーの承認・停止、プロジェクト数や同時起動数の上限を、管理画面で変えられます
- **テスト**: Docker を差し替えて、停止の判定、データの保持、トークンの更新、自動判定などを、テストで確かめています。100 件近くあります
