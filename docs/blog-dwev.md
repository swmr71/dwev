# GitHub のリポジトリを URL ひとつで動かす「dwev」を作った(BETA)

友だちと作っているアプリを、「手元で動かさなくても、URL を送れば見てもらえる」ようにしたくて、自前のプレビューサーバー **dwev** を作りました。

GitHub のリポジトリ URL とブランチを入れて「作成して起動」を押すと、ビルドして、`https://〜-dev.example.com` のようなプレビュー URL が発行されます。

> **BETA / ベストエフォート**です。動作や稼働の保証はなく、予告なく止まったり、データが消えたりします。

## できること

- リポジトリとブランチを指定するだけで、Docker でビルドして起動する
- Dockerfile が無くても、**Node / Django / FastAPI / Flask を自動判定**して、Dockerfile を作る
- プライベートリポジトリも、GitHub App で許可したものだけ読み取れる(読み取り専用)
- スマホからでも操作できる(設定の編集は専用のダイアログ)
- 停止しても、書き込んだデータは残る

## 構成

```
ブラウザ ─ Cloudflare Tunnel ─ Traefik ─ 各プロジェクトのコンテナ
                               └─ dwev 本体 (Node / Express + SQLite)
                                     └─ socket-proxy ─ Docker API
```

- 公開は **Cloudflare Tunnel** で行うので、サーバーのポートは開けません
- プロジェクトごとにサブドメインを発行し、**Traefik** が Host で振り分けます
- Docker の操作は、**socket-proxy** を挟んで、必要な API だけを許可しています
- 本体は Node / Express で、状態は `node:sqlite` に持たせています

## 一番気をつけたのは「他人のコードを動かす」こと

このサービスは、承認した人が書いたコードを、そのまま動かします。そのため、リソースと権限は、かなり絞りました。

**実行時の制限**

| 項目 | 上限 |
|---|---|
| メモリ | 256MB |
| CPU | 0.5 コア |
| プロセス数 | 128 |
| 稼働時間 | 最大 1 時間 |

CPU は、使った時間をミリ秒で数えています(Docker の stats API から取っています)。

**ビルドの制限**

`docker build` は、依存パッケージのインストールなど、任意のコマンドを実行できます。そこで、次のようにしました。

- メモリ・CPU・時間に上限をかける
- ビルド用のコンテナを、実行時と同じ**専用のネットワーク**に置いて、ホストの管理用のアドレスへは届かないようにする
- CLI の buildkit では、ビルドごとにネットワークを指定できないので、**Docker の API で直接ビルド**する

**GitHub のトークン**

プライベートリポジトリの clone には、GitHub App の「ユーザートークン」を使います。

- 権限は、Contents の**読み取りだけ**
- トークンで読める範囲は、「アプリに許可されたリポジトリ」と「ログインした本人の権限」の**重なり**だけ。組織の外の人が使っても、その組織のリポジトリは読めません
- 保存するときは暗号化し、clone のときだけ使う。コンテナにも、ログにも出さない(エラーメッセージからは、伏せ字にする)

## Aternos 方式の「まだ使っていますか?」

放っておくと、サーバーのリソースが、使われないまま埋まっていきます。そこで、Minecraft のサーバーサービスの Aternos のように、**10 分ごとに「まだ使っていますか?」を出す**ことにしました。

- 押さないと、猶予時間のあとに、自動で停止する
- 全画面で、赤く脈打つ警告にした(見逃されたので)
- Bot に押させないよう、**Cloudflare Turnstile** で確認する。トークンは、ホスト名・アクション・プロジェクト ID に結び付ける
- 将来、ここに広告を出せるように、枠だけ用意してある

## ハマったところ

**停止の判定が、最大 60 秒遅れた**
タイマーが 0:00 になっても、止まりませんでした。見回りの処理が、1 分に 1 回だったからです。判定だけを 5 秒ごとにして、重いサンプリング(CPU の計測など)は 60 秒ごとのままにしました。

**停止のたびに、データが消えた**
最初は、停止するとコンテナを削除していました。SQLite を使うアプリでは、毎回データが消えます。**コンテナを消さずに止める**方式にして、設定の変更や再ビルドのときだけ、作り直すことにしました。

**iOS の `prompt()` は、改行を入力できない**
環境変数の編集に `prompt()` を使っていたら、スマホで複数行を書けませんでした。専用の編集ダイアログを作りました。

**`mysqlclient` がビルドできない**
`python:slim` には、コンパイラも `pkg-config` もありません。自動生成する Dockerfile で、`mysqlclient` や `psycopg2` が依存に入っているときだけ、必要なライブラリを apt で入れるようにしました。

**落ちたコンテナが「実行中」のまま**
アプリが落ちても、画面は「実行中」でした。コンテナの終了を見つけたら、終了コードや、メモリ不足(OOM)かどうかを理由にして、失敗にするようにしました。

## 動かす側でもハマった(Django を動かしたとき)

実際に Django のアプリを動かして、よくある罠にいくつか当たりました。同じことをやる人の参考に残します。

- **`no such table`**: Dockerfile の起動で、`migrate` が走っていませんでした。`ENTRYPOINT` で `migrate` してから、元の `CMD` を `exec` する形にして、解決しました
- **管理者がいない**: `createsuperuser --noinput` と、環境変数 `DJANGO_SUPERUSER_*` で自動作成しました。カスタムユーザーモデルだと、`USERNAME` ではなく、そのモデルのログイン項目名(例: `USER_ID`)が必要です
- **ワーカーが `SIGKILL`**: gunicorn のワーカー数が多くて、メモリ上限(256MB)を超えていました。ワーカーを減らして解決しました。「CSS が最初だけ付かない」という症状も、これが原因だったようです
- **`403 CSRF`**: プロキシの後ろでは、Django は自分を http だと思っています。`CSRF_TRUSTED_ORIGINS` に、`https://` 付きの URL を入れる必要があります
- **Service Worker のキャッシュ**: PWA にしていると、古いページや、古い CSRF トークンが残ります。環境を変えたら、サイトデータを消すのが確実です

## 使ってみたい人へ

まだベータ版です。承認制で、少人数だけに公開しています。

- 大事なデータや、本番の運用には使わないでください
- コードは、必ず GitHub に残してください
